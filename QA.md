# Registro de QA

Bitácora de qué se prueba en cada fase del proyecto, complementaria a la suite automatizada en `tests/` (`pytest`). Se actualiza a medida que avanzan las fases de `CLAUDE.md`, para tener evidencia de qué quedó cubierto y qué no en cada versión.

## Cómo correr las pruebas

```bash
transcriptor-env/bin/python -m pytest tests/ -v
```

No toca `escuela.db` (la base de desarrollo real) ni `transcriptions_history.db` — cada test de API usa una SQLite en memoria aislada (`tests/conftest.py`).

## Pipeline de IA (Gradio + Ollama) — validación con datos reales (2026-08-27)

El prototipo Gradio ya se había probado antes solo con audio corto/de prueba. Para esta ronda se descargó un video real de YouTube (una clase grabada tipo curso, ~47MB de audio) usando la propia función `infraestructura/youtube.py` que ya usa la UI, y se corrió todo el pipeline real de punta a punta:

- **Transcripción** (`servicios/servicio_transcripcion.py`, motor `faster-whisper-tiny`, GPU): 37.605 caracteres / 6.579 palabras / 601 segmentos SRT en 40.4s. Confirma que FFmpeg + faster-whisper + formato SRT aguantan un audio largo real, no solo clips cortos.
- **Material de estudio** (`servicios/servicio_material_estudio.py`, `llama3.2:3b` vía Ollama): al ser >6.000 caracteres, activó el chunking map-reduce por primera vez con datos reales — **7 bloques condensados secuencialmente**, resumen + puntos clave + hoja de repaso + 6 tarjetas (`{pregunta, respuesta}`) generados correctamente en 84.9s.

El audio descargado y la transcripción de prueba se borraron después de esta validación (misma política de privacidad que sigue la app: no se guarda audio, y acá tampoco se guardó como dato de prueba permanente).

**No cubierto por esta prueba:** el contenido generado no se guardó en `escuela.db`/`ContenidoClase` — ese pipeline (Gradio) y el backend nuevo (FastAPI) siguen sin conectarse, como ya se documentó arriba.

## Fase 1 — Backend FastAPI y modelo de datos (2026-08-27)

**Automatizado** (`tests/test_validadores.py`, `tests/test_api.py`, 20 tests):
- Validación de RUT: válido con/sin puntos, dígito verificador `K`, dígito verificador incorrecto, formato inválido, vacío.
- CRUD de Colegio: crear, listar, 404 en inexistente.
- Curso: crear (genera `codigo_invitacion` de 6 caracteres), 409 si `colegio_id` no existe.
- Bloque: crear bajo un curso, listar, 409 si `profesor_id` no existe, 422 si `dia_semana` fuera de rango (0-6).
- Usuario: crear con roles, 422 si el RUT es inválido, 409 si el RUT está duplicado, 409 si `colegio_id` no existe, 404 en inexistente.
- `/salud` y `/docs` responden.

**Probado manualmente antes de automatizar** (vía `curl`, ver historial de la sesión): flujo completo colegio → curso → bloque → usuario contra un `escuela.db` real, migrado con Alembic; confirmado que `python app.py` (Gradio) sigue arrancando sin verse afectado por las dependencias nuevas (`sqlalchemy`, `alembic`, `pytest`).

**Modelo ORM directo** (`tests/test_modelo_orm.py`, 8 tests — `Clase`/`ContenidoClase`/`AlumnoCurso` no tienen rutas CRUD todavía, así que se prueban contra la sesión de SQLAlchemy directamente, no vía API):
- `ContenidoClase` guarda y recupera datos con forma real de transcripción (texto largo, SRT multilínea, acentos, `¿¡`, tarjetas como lista de dicts `{pregunta, respuesta}`) sin pérdida — confirmado releyendo desde la base, no solo el objeto en memoria.
- `Bloque.hora_inicio`/`Clase.fecha` se recuperan como `datetime.time`/`datetime.date` reales, no strings.
- Cascadas: borrar un `Bloque` borra sus `Clase`s y `ContenidoClase`; borrar un `Curso` borra sus `Bloque`s.
- Borrar un `Colegio` con `Usuario`/`Curso` dependientes falla (`IntegrityError`) — no hay cascada ahí a propósito, para no destruir datos por accidente.
- `UsuarioRol` no permite el mismo rol dos veces en el mismo usuario, pero sí permite roles distintos (ej. PROFESOR + UTP) en un mismo usuario.
- `AlumnoCurso` no permite que el mismo alumno se una dos veces al mismo curso.

**Migración Alembic** (validado a mano contra una copia descartable, no contra `escuela.db`): ciclo `upgrade head` → `downgrade base` → `upgrade head` limpio, sin errores — confirma que la migración inicial es reversible, no solo que "corrió una vez".

**Fuera de alcance todavía** (no hay nada que probar aún — llega en fases futuras):
- Frontend (Fase 3), control de clase en vivo (Fase 4), cola EDF (Fase 5).
- Integración real con el pipeline de Gradio: nada llena `ContenidoClase` con datos reales todavía — eso es la Fase 4.

## Instalación desde cero como usuario nuevo (2026-09-03)

Se siguió el README literalmente en una máquina Linux limpia (Nobara/Fedora 44, sin Docker/Ollama/venv previos) para medir qué tan "sin fricción" es la instalación real — no solo si el código corre, sino si el proceso documentado alcanza para un usuario nuevo sin ayuda. Resultado: la app terminó levantando correctamente (`python app.py` → interfaz Gradio en `http://127.0.0.1:7862`, HTTP 200, config y DB del historial generados solos), pero el camino documentado en ese momento no llegaba solo — se encontraron y corrigieron 3 problemas:

1. **`numpy==1.26.4` no soporta Python 3.14+.** El único Python del sistema de prueba era 3.14 (recién liberado); `numpy` no tiene wheel para esa versión y falla al compilar desde fuente por falta de `python3.14-devel`. No había ninguna nota de versión mínima/máxima de Python en el README. **Fix**: se agregó la restricción "Python 3.10 a 3.13" como paso 0 en `README.md` y `docs/Notas_de_Instalacion.md`, con el comando de instalación de una versión soportada por distro. Se resolvió instalando `python3.12` aparte (`sudo dnf install python3.12 python3.12-devel`) y creando el venv con ese binario. **Corrección (2026-09-04)**: ese rango estaba mal — nunca se probó Python 3.13 realmente, solo se asumió que funcionaba. Verificando después contra los archivos publicados en PyPI, `numpy==1.26.4` tampoco tiene wheel para 3.13 en ningún sistema operativo (solo publica `cp39` a `cp312`). El rango correcto y ya corregido en ambos README es **Python 3.10 a 3.12**.
2. **`deepfilternet` rompía la instalación completa.** Es una dependencia usada solo por el modo opcional `'deepfilter'` de `infraestructura/mejorador_audio.py` (que ya la importa de forma perezosa y cae a otros modos si falta), pero al estar listada sin marcar en `requirements.txt`, su dependencia `deepfilterlib` (compila una extensión nativa en Rust, sin Cargo instalado por defecto) hacía fallar `pip install -r requirements.txt` completo — ni gradio, ni fastapi, ni sqlalchemy llegaban a instalarse. **Fix**: se sacó `deepfilternet` de `requirements.txt` a un archivo aparte opcional (`requirements-deepfilter.txt`), documentado en ambos README como paso opcional que requiere Rust/Cargo.
3. **La instalación "sin GPU" descargaba ~1.5GB de paquetes CUDA de todos modos.** `pip install torch==2.13.0 torchaudio==2.11.0` sin índice explícito resuelve, incluso en la rama "Sin GPU" del README, a una build de PyPI con CUDA 13 empaquetado (`nvidia-cublas`, `nvidia-cudnn`, etc.) — el mismo tipo de problema que el propio `requirements.txt` ya advertía para el caso GPU NVIDIA, pero también aplicaba al caso CPU. **Fix**: se cambió el comando "Sin GPU" en ambos README a `--index-url https://download.pytorch.org/whl/cpu` (build `+cpu` real, confirmada disponible para `torch==2.13.0`/`torchaudio==2.11.0` en `cp312`), evitando la descarga innecesaria en el hardware modesto que es el objetivo del proyecto.

**No cubierto por esta prueba:** instalación en Windows (el target real de despliegue) ni la vía Docker Compose — solo se probó el camino nativo en Linux.

## Instalación desde cero en Windows con Conda (2026-09-04)

Validación en Windows 11 real con GPU dedicada (NVIDIA GeForce RTX 2050, driver 32.0.16.1664), sobre un entorno Conda (`transcriptor-env`, Python 3.12.14) ya preparado por una sesión anterior en la misma máquina cuyas notas habían quedado sin commitear. El único bloqueador real, en Windows igual que en Linux, es `numpy==1.26.4` (sin wheel para 3.13+ en ningún SO). Se corrigió el texto en `README.md`, `docs/Notas_de_Instalacion.md` y `docs/Guia_Instalacion_Windows.md` para no seguir citando una razón que no es cierta.
3. **`docs/Guia_Instalacion_Windows.md` afirmaba que `app.spec` y `construir_exe.py` ya "estaban preparados en el repositorio"** para el empaquetado con PyInstaller — falso, ninguno de los dos archivos existe (`ls` lo confirma, y no están en ningún commit). 4. **PyTorch con CUDA 12.6, verificado de verdad**: con `torch==2.13.0`/`torchaudio==2.11.0` instalados vía `--index-url https://download.pytorch.org/whl/cu126` en el env existente, `torch.cuda.is_available()` devuelve `True` y `torch.cuda.get_device_name(0)` reconoce la RTX 2050; `infraestructura.hardware.detect_gpu_vendor()` devuelve `'nvidia'`.
5. **Pruebas automatizadas, corridas de verdad**: `python -m pytest tests/ -v` → **43 passed, 3 warnings en 3.85s** (mismos warnings conocidos que en Linux, ver más arriba).
6. **La app arranca y sirve, verificado con una petición HTTP real**: `python app.py` (mismo entry point que Linux) levantó Gradio en `http://127.0.0.1:7862`; `Invoke-WebRequest` contra esa URL devolvió `HTTP 200`.

**No cubierto por esta prueba:** instalación desde cero real (sin un Conda/env ya preparado de antemano) — se reusó el entorno que ya existía en la máquina en vez de crear uno nuevo desde el Windows recién instalado. Los pasos de `docs/Guia_Instalacion_Windows.md` para crear el entorno están documentados pero no se re-ejecutaron paso a paso en esta sesión.

## Instalación sin Conda (solo Python) en Windows (2026-09-05)

El usuario pidió explícitamente que la instalación fuera fácil para alguien que solo tiene Python, no Conda. Se probó el camino alternativo de punta a punta:

1. **Python 3.12 "de verdad" (python.org, sin Conda), instalado sin admin**: `winget install --id Python.Python.3.12 -e --scope user` — quedó instalado en `%LOCALAPPDATA%\Programs\Python\Python312`, sin tocar Program Files. 2. **Entorno con `venv` puro (sin Conda) en un venv nuevo**: `python -m venv`, luego `pip install torch==2.13.0 torchaudio==2.11.0 --index-url .../cu126`, luego `pip install -r requirements.txt` — **ambos completaron al 100% sin errores ni compilador C**, igual que con Conda. `pytest tests/ -v` → **43 passed** de nuevo. `detect_gpu_vendor()` → `nvidia`. `python app.py` levantó Gradio y sirvió correctamente. **Conclusión: Conda nunca fue necesario** — el README y `Notas_de_Instalacion.md` sobre-recomendaban Conda como camino principal en Windows; se corrigió para que `venv` (stdlib, sin instalar nada extra) sea el camino principal y Conda quede como alternativa para quien ya lo use.

## Endurecimiento de contraseñas, inyección SQL y tokens (2026-10-01)

Pedido: que las contraseñas sean sólidas y que no sea posible la inyección SQL ni otras vulnerabilidades. Detalle de qué se hizo y los límites que quedan: `docs/fases/fase-2-autenticacion-roles.md`, sección "Endurecimiento".

**Inyección SQL — auditoría**: se buscó SQL armado a mano en `interfaz/`, `infraestructura/`, `servicios/` y `nucleo/`. Solo hay `PRAGMA foreign_keys=ON` (constante) en `basedatos.py` y el historial del prototipo Gradio, cuyas tres sentencias son constantes o usan `?`. Todo lo demás es ORM. Se dejó un test que lo vigila (`test_no_hay_sql_armado_a_mano_en_el_backend`) y otro que envía 10 payloads clásicos (`' OR '1'='1`, `'; DROP TABLE usuarios; --`, `UNION SELECT`, byte nulo...) a login de staff y alumno, restablecer PIN, setup y unirse (con y sin código válido): ninguno entrega un token ni causa un 500, y los mismos textos guardados como nombre de curso vuelven idénticos (se tratan como datos).

**Hallazgos corregidos**
1. **Sin política de contraseñas**: se aceptaba cualquier contraseña de personal, incluso `x`. Ahora 10-128 caracteres, ≥ 4 distintos y sin el RUT.
2. **Sin tope de largo**: un login con 100 000 caracteres iba a argon2. Ahora 422 antes de hashear.
3. **PIN trivial**: `111111`, `123456`, etc. se podían elegir. Ahora se rechazan al elegir el PIN.
4. **Enumeración de RUT por tiempo de respuesta**: login con RUT inexistente respondía en 3 ms contra 57 ms con un RUT real (mediana de 7, base en memoria). Ahora 59 ms.

## Fase 4, parte 1: backend del control de clase en vivo (2026-10-01)

*Decisión*: la grabación sirve **con un PC de la sala o con el celular del profesor, las dos opciones válidas**, con una sola pieza: una sesión de grabación por clase (`Grabacion`, migración `d7a2c9e4b6f1`) cuyo estado guarda el servidor. Quien **controla** (el celular, o el mismo equipo que graba) manda comandos (`iniciar`, `pausar`, `reanudar`, `silenciar`, `activar_audio`, `terminar`, `cancelar`, `marcar_prioritaria`); el equipo **grabador** (cualquier navegador que se registre) consulta ese estado con su latido y obedece, y sube el audio en trozos. Para cambiar de equipo a mitad de clase (por ejemplo, el celular se queda sin batería) basta con registrar otro con `forzar`; el anterior se entera por su latido (409) y debe parar.

*Reglas*: solo desde la red del colegio y solo el profesor de ese bloque (ni UTP ni otro profesor); solo un bloque de clase de hoy y hasta 15 minutos después de su término (`MINUTOS_CORTE_GRABACION`); no se puede iniciar sin un equipo grabador conectado; el corte automático termina la grabación pasado el término + gracia, o si no hay ningún equipo conectado por 10 minutos, y si el equipo no finaliza en 45 s el servidor procesa lo que llegó. Al terminar: se unen los trozos, se transcribe, se genera el material y queda **por aprobar** (el flujo de revisión de siempre); **el audio se borra siempre**, también si falla (en `finally`), y tras un reinicio se borra cualquier carpeta huérfana. Si falla la generación (p. ej. Ollama apagado) la transcripción se conserva oculta a los alumnos y la sesión queda en error con el motivo; un reintento vuelve a empezar la misma sesión.

*Red local*: se decide en el servidor (no en el frontend). Una conexión es local si viene de una dirección de la red del colegio (127/8, 10/8, 172.16/12, 192.168/16, enlace local, ::1, fc00::/7, fe80::/10) **y no trae cabeceras de proxy** (`X-Forwarded-For`, `CF-Connecting-IP`, `X-Real-IP`, `Forwarded`): un túnel de Cloudflare se conecta desde este mismo equipo, y sin esa segunda regla parecería local. Hallazgo al probar: `ipaddress.is_private` de Python da `True` para rangos de documentación como 203.0.113.0/24, así que se usa una lista explícita. *Límite*: detrás del proxy de Vite en desarrollo el servidor siempre ve 127.0.0.1.

*Trozos de audio*: cuerpo crudo `audio/*`, tipo permitido (webm, ogg, mp4, mpeg, wav), el primer trozo debe tener la firma del formato (no basta con decir `audio/webm`), tope por trozo (8 MB, se corta la lectura apenas lo supera) y por grabación (500 MB), nombre de archivo puesto por el servidor (el número de trozo), un reintento reemplaza y no duplica, y solo el equipo grabador registrado puede subir.

*Pruebas*: 37 tests nuevos (`tests/test_grabaciones.py`), `pytest tests/` **201 passed**. Se quitó cada defensa, una a la vez (27 mutaciones: guardia de red, cabeceras de proxy, dueño de la sesión y del bloque, tipo, firma, tamaños, equipo grabador, cambio de equipo, borrar el audio siempre, corte por hora y por falta de equipo, finalización por el servidor, solo hoy, después del corte, clase con material, reinicio) y a las 27 les falló su test; tres sobrevivían al principio por estar cubiertas por otra defensa y se agregaron pruebas que las ejercitan solas. El procesamiento pesado (Whisper, Ollama) está reemplazado en estos tests; la prueba con el pipeline real va aparte. *Aún no*: pantallas del frontend, ni la prueba de punta a punta con voz real.

*Prueba con el pipeline real (2026-10-01)*: servidor real sobre la base de demostración, GPU NVIDIA, Whisper `small` y Ollama. Se sintetizó una frase en español con una voz de Windows, se pasó a webm/opus (38 KB), se partió en 7 trozos de 6 KB (cortes arbitrarios, como los de un navegador) y se subió por la API como lo haría un equipo grabador: la unión de los trozos se transcribió **correctamente** ("Hoy vamos a estudiar la fotosíntesis. Las plantas usan la luz del sol, el agua y el dióxido de carbono para producir glucosa y oxígeno.") y la carpeta de audio ya no existía al terminar. *Hallazgo*: la generación falló porque el modelo por defecto (`llama3.2:3b`, lo que elige `ollama_model: auto` con GPU) no está instalado en este PC (solo hay `qwen2.5vl:3b`). Eso fue un caso real de lo que el diseño debía soportar: la sesión quedó en error con el motivo, la transcripción se conservó oculta y, como el audio ya no existe, **no había forma de reintentar sin volver a grabar** → se agregó `POST /grabaciones/{id}/regenerar` (genera de nuevo desde la transcripción guardada; la sesión con error se puede retomar; 5 tests más y 3 mutaciones cazadas, `tests/test_grabaciones.py` 39 passed). ## Que una falta de memoria no tumbe el servidor del colegio (2026-10-02)

Pedido del usuario: un corte por memoria es peligroso en un PC de colegio. *Qué pasaba*: el procesamiento de una clase corría en un hilo del mismo proceso que atiende la plataforma; si se agotaba la memoria, el sistema (o Claude Code, que cortó dos veces las pruebas largas) cerraba **todo**. *Ahora, por capas*: (1) **proceso aparte** (`servicios/trabajador.py`): transcribir y generar el material corre en otro proceso; el servidor lo lanza, espera su código de salida y, si falló, deja la clase en error con el motivo; (2) **vigilante y tope**: el trabajador mira su propia memoria cada segundo y, si pasa del tope (60 % de la RAM del equipo, máximo 8 GB; `LIMITE_MEMORIA_PROCESAMIENTO_GB` lo cambia), se cierra con el código 75 antes de que el sistema tenga que elegir qué cerrar; el servidor reconoce ese código y dice «el equipo no tenía memoria suficiente... cierra otros programas y pulsa Reintentar»; (3) **espera de memoria**: antes de lanzarlo espera hasta 10 min a que haya 2,5 GB libres (`MEMORIA_MINIMA_PROCESAMIENTO_GB`), y si no, deja la clase en error sin haber tocado nada; (4) **un procesamiento a la vez** y con **tiempo máximo** (4 h, `TIEMPO_MAXIMO_PROCESAMIENTO_HORAS`): uno atascado se mata de verdad y no bloquea al servidor; (5) **el audio siempre se borra**, lo cierre bien o mal el trabajador (también si el sistema lo mata); (6) **Ollama**: suelta el modelo al minuto (`keep_alive`; antes 5 minutos con 1,6 a 4,8 GB retenidos) y, si el modelo lo eligió la aplicación (`auto`) y no cabe en la memoria libre, usa el de 1B; (7) **un reinicio no pierde la clase**: si el servidor se reinicia (corte de luz) con una clase procesándose, su audio sigue en disco y se vuelve a procesar al arrancar; si solo faltaba el material se regenera desde la transcripción; si el trabajador sigue vivo no se duplica el trabajo (archivo con su número de proceso). ## Reintentos automáticos: el servidor se recupera solo (2026-10-02)

## Tema claro u oscuro opcional (2026-10-02)

Pedido del usuario: modo oscuro o claro, opcional. `lib/tema.ts` (claro / oscuro / **sistema**, que es el valor por defecto y sigue los cambios del sistema mientras se use) pone o quita la clase `dark` de la página y `color-scheme` (así también cambian las barras de desplazamiento y los controles nativos), se aplica antes de dibujar la app (sin destello claro) y se recuerda en `localStorage` (si el navegador lo bloquea, funciona igual mientras la página siga abierta). `SelectorTema`: grupo «Tema de color» con tres botones, cada uno con su texto (visible en la barra lateral y al pie; solo para el lector de pantalla cuando son íconos) y `aria-pressed`; en el PC está en la barra lateral, en el teléfono y en la entrada, al pie. Los colores que estaban escritos a mano (estados de la clase y de la grabación, avisos, colores por asignatura, la nota de éxito) recibieron 77 variantes `dark:` con un guion que mapea cada par claro→oscuro; el código del QR sigue sobre blanco para que se pueda escanear. **Mermaid**: en oscuro dibuja con su tema oscuro (directiva `init`, que con `securityLevel: 'strict'` no puede cambiar nada de seguridad) y se vuelve a dibujar al cambiar de tema; el Word y la hoja del PDF usan siempre el claro, y la impresión fuerza `color-scheme: light`.

## Prueba de punta a punta de las fotos de la pizarra, con el servidor, el trabajador y los modelos reales (2026-10-02)

Hasta ahora las piezas se habían probado por separado. Se armó un guion (servidor `uvicorn` real, base temporal con las migraciones, trabajador real en proceso aparte, Whisper, el modelo de visión `qwen2.5vl:3b` y `llama3.2:3b` de Ollama, la voz real de prueba y las fotos reales del usuario) con cuatro escenarios.

*Feliz* (voz + 3 fotos: la tarea, la pizarra de direcciones IP y la lista de librerías): subidas aceptadas (201); un archivo que no es foto (415), un usuario sin permiso (403) y sin sesión (401) rechazados; **130 a 145 s** de procesamiento en total (con la GPU de 4 GB de este PC, no en el equipo del colegio); las 3 fotos leídas; imágenes y audio borrados al terminar; una foto después de terminar, rechazada (409); el alumno **no ve la clase antes de aprobar (404) y después ve las 3 partes**; el profesor corrige una y quita otra y el alumno ve el cambio; el mapa conceptual salió con 5 a 6 relaciones. *Sin el modelo de visión instalado*: la clase termina igual (72 s) y cada foto dice «ejecuta `ollama pull ...`». *Falta de memoria* (tope de 0,4 GB): el trabajador se corta, las fotos quedan **pendientes con sus imágenes** y el audio se conserva; tras reiniciar el servidor y reintentar, la clase termina con las fotos leídas y todo borrado. *A la fuerza* (el trabajador muerto con `Stop-Process` justo después de leer la primera foto): la leída ya no tiene imagen, las otras dos siguen pendientes con la suya, y el reintento las lee y termina.

**Defecto real que encontró la prueba**: con una pizarra de cálculo densa el modelo entró en un **bucle de repetición** y Ollama abortó con «token repeat limit reached»; peor, **todas las fotos siguientes fallaban también** (hasta con la más simple) mientras el modelo siguiera cargado. Se aislaron las causas: (1) a **1280 px** se abortaba siempre y a **1024 px** (con lo que se había medido en la factibilidad) no: ahora las fotos se guardan a 1024; (2) aun así el modelo no es determinista (con el mismo prompt a veces repetía el bloque entero hasta el tope de palabras, a veces no): `limpiar_repeticiones` deja una sola vez toda línea larga que sale tres veces o más; (3) si Ollama aborta, el modelo se **descarga** (así se recarga limpio), se reintenta una vez con la foto a 768 px y más penalización a repetir, y si vuelve a fallar se descarga otra vez para no dejar mal a las fotos siguientes; si el modelo ni siquiera está instalado no se reintenta. 8 tests nuevos (`test_pizarra.py`), 9 mutaciones cazadas. También se comprobó que una foto de **12 MP (814 KB)** sube en 0,2 s y queda guardada a 61 KB.

*Lo que no cubre*: tiempos en un equipo de 4 núcleos sin GPU (cada foto tardaría varios minutos: medido en la factibilidad, 5 a 35 s por foto con 4 núcleos físicos rápidos; en un equipo más lento, más), una foto sacada con una cámara de celular real, y un modelo de visión con una pizarra de verdad de sala con reflejos.

## Mediciones solo con CPU, por separado: clase y fotos (2026-10-02)

Pedido del usuario: repetir las mediciones de antes solo con CPU y anotar en el README, por separado, la transcripción y el resumen (núcleo) y las imágenes (opcional), para que cada colegio elija si quiere tenerlas. Por eso las fotos pasaron a ser **opcionales** (`FOTOS_PIZARRA=si`, apagadas por defecto: sin botón, y el servidor rechaza la subida con 403).

*Método* (`correr_cpu.ps1`, sin tocar nada más del equipo mientras corría): una instancia de Ollama sin GPU limitada a los núcleos del perfil (afinidad de procesador), y la aplicación creyendo que el equipo tiene ese número de núcleos (usa uno menos para dejarlo libre al servidor); la clase real de 92 min por el flujo real (conversión, limpieza `light_dsp`, Whisper `small` por tramos, resumen con 1B y con 3B), y las 6 fotos con el código real de `servicio_pizarra` (a 1024 px, ya normalizadas como al subirlas). *Resultados*: ver las tablas del README. Resumen: **4 núcleos**: transcripción 16,9 min (conversión 6 s, limpieza 43 s, Whisper 963 s; pico de memoria 2,03 GB; 12.495 palabras), resumen 2,4 min con 1B y 17,5 con 3B; fotos 2,7 min las 6 (14 s la primera, mediana 34 s). **8 núcleos** (4 rápidos y 4 de eficiencia): transcripción 22,3 min (Whisper 1265 s), resumen 2,3 min con 1B y 11,6 con 3B; fotos 3,1 min (19 s la primera, mediana 42 s). Ninguna foto necesitó reintento ni dio error.

*Hallazgos*: (1) la **transcripción fue más lenta con 8 núcleos que con 4**: este procesador mezcla 4 núcleos de rendimiento con 4 de eficiencia y Whisper reparte el trabajo por igual, así que espera a los lentos; en cambio el resumen con 3B sí ganó (17,5 → 11,6 min). Un PC con 8 núcleos iguales no está medido. (2) **Leer fotos no mejora con más núcleos** (2,7 y 3,1 min): es cuestión de ancho de banda de memoria. (3) **Variación entre corridas**: la transcripción de 4 núcleos dio 13,2 min en la medición anterior y 16,9 ahora, con el mismo código de Whisper (la diferencia está en el procesador compartido con el resto del sistema); se advierte en el README. (4) La memoria de la transcripción subió de 1,70 a 2,03 GB respecto de la medición anterior (la limpieza de audio ya está incluida).

*Limitaciones*: un solo procesador de laptop, rápido y de 13.ª generación; el perfil de «8 núcleos» es híbrido y no representa a uno de 8 núcleos iguales; una sola clase de 92 minutos (no una jornada); fotos sacadas de una carpeta, no con una cámara de celular de la sala.
